## Context

ADR 0007 puts per-frame evaluation in the client: at 60 Hz Godot interpolates baked tables and poses the
train itself, and no RPC is issued from `_process`. It also states that *"algorithms duplicated on both sides
(frame interpolation, trainset chain) are validated against `shared/golden/*.json` generated by the backend"*.

This task builds the backend half of that arrangement. The module produced here is **not on the runtime
path** — the client will own the running implementation (T-123). It exists to be the float64 reference that
the client is measured against, and to serve headless and CLI use.

Getting the semantics exactly right matters more than performance. A train looks wrong in a very specific,
immediately visible way when the chain is wrong: bogies drift off the rails, or car bodies bend along the
curve instead of cutting across it as rigid bodies do.

## Contract

### The algorithm

Given an `Alignment`, a `Trainset` and a lead station, produce a pose for every car and every bogie.

**Station layout.** `s_lead` is the station of the **front face of the first car**. Working backwards along
the consist, with `d = direction` (`+1` forward, `−1` reverse):

```
car i front face   f_i
car i rear face    r_i = f_i − d · length_i
car i lead pivot   p_i,lead  = f_i − d · (length_i − pivot_distance_i) / 2
car i trail pivot  p_i,trail = p_i,lead − d · pivot_distance_i
car i+1 front face f_{i+1} = r_i − d · coupling_gap
```

All of these are **stations**, i.e. arc length along the alignment, not chord distances. This is the standard
approximation and the one COYPU's own semantics imply; do not attempt an exact chord-constrained solve.

Stations that fall outside `[station_start, station_end]` must be clamped, and a flag raised on the result so
the client and the UI can tell that the consist is partly off the modelled alignment rather than silently
piling cars up at the end.

**Bogie pose.** Each pivot station is evaluated with `frames(alignment, s, pivot)`. The bogie's position is
the frame `origin` — the track-plane centre, which already accounts for the `RotationPivot.LOW_RAIL`
convention. The bogie's orientation is the frame basis itself: bogies follow the track exactly, including
cant roll and gradient pitch.

**Car body pose.** The body is rigid and spans its two pivots:

```
origin   = (P_lead + P_trail) / 2                       # 3-D midpoint of the two pivot POSITIONS
forward  = normalize(P_lead − P_trail)                  # the chord, not the tangent
roll     = (roll_lead + roll_trail) / 2                 # mean of the two frames' cant roll
up_raw   = normalize(up_lead + up_trail)                # mean of the two frames' plane normals
up       = normalize(up_raw − (up_raw · forward) · forward)   # Gram-Schmidt against forward
left     = cross(up, forward)
```

> **Corrected 2026-09-18 (F11).** This formula originally read `normalize(P_lead − P_trail) · d`, which is
> wrong: the layout formulas already put `p_lead − p_trail = d · pivot_distance`, so the normalised chord is
> `d · tangent` and the extra `· d` squared the sign away, leaving `forward` equal to `+tangent` for both
> directions — contradicting acceptance criterion 5. The direction sign is carried entirely by which pivot
> the layout assigns as lead. See `docs/data-contracts/trainset-chain.md`, "On `forward`'s sign".

The chord — not the tangent at the midpoint — is what makes a car cut across a curve the way a real vehicle
does. Applying the mean roll and then orthogonalising in exactly this order is part of the contract: the
client must reproduce the same sequence to match the golden.

A single-bogie or zero-pivot-distance car (`pivot_distance == 0`) degenerates; fall back to the frame at the
car centre and document it.

### API

```python
@dataclass(frozen=True)
class BogiePose:
    station: float
    position: np.ndarray        # (3,) (E, N, H)
    tangent: np.ndarray         # (3,)
    left: np.ndarray            # (3,)
    up: np.ndarray              # (3,)
    roll: float
    pitch: float

@dataclass(frozen=True)
class CarPose:
    index: int
    station_front: float
    station_rear: float
    lead: BogiePose
    trail: BogiePose
    origin: np.ndarray          # (3,) body centre (E, N, H)
    forward: np.ndarray         # (3,) unit, chord direction, already signed by travel direction
    left: np.ndarray            # (3,) unit
    up: np.ndarray              # (3,) unit
    roll: float

@dataclass(frozen=True)
class TrainsetPose:
    station_lead: float
    direction: int
    cars: tuple[CarPose, ...]
    clamped: bool               # any station fell outside the alignment

def pose_trainset(
    alignment: Alignment,
    trainset: Trainset,
    station_lead: float,
    direction: int = 1,
    pivot: RotationPivot | None = None,
) -> TrainsetPose: ...

def pose_trainset_many(
    alignment: Alignment,
    trainset: Trainset,
    station_lead: np.ndarray,
    direction: int = 1,
    pivot: RotationPivot | None = None,
) -> tuple[TrainsetPose, ...]: ...
```

`pose_trainset_many` exists so golden generation and any headless batch use evaluate a whole run in one
vectorised pass over `frames()` rather than one call per station. Prefer a single `frames()` call over all
pivot stations at once.

## Invariants

- **`domain/` is pure** — numpy only here.
- **ADR 0007:** this module is a reference, not a runtime path. Do not wire it into a per-frame protocol
  method, and do not let any handler call it once per frame.
- **ADR 0006:** mode-agnostic. The chain must work for the tram fixture's 1000 mm-gauge network as written,
  with no branch on `Mode`. Test it.
- **ADR 0004:** float64 throughout the domain; the float32 conversion happens only when writing the golden
  and on the wire.
- `lrs.frames` stays the single place cant roll is applied — do not recompute roll here.

## Acceptance criteria

1. Bogie positions lie on the alignment: `project_xy(alignment, bogie.position[:2])` returns the pivot
   station to within 1 mm and a lateral offset within 1 mm, for every sample.
2. Body centres lie *inside* curves relative to the track centreline — assert that the body origin's lateral
   offset from the alignment is non-zero and on the inside of the curve for the sharpest-curve sample, and
   that its magnitude matches the mid-ordinate of the chord to within 1 mm.
3. On a straight with zero cant and zero gradient, body `forward` equals the frame tangent to `1e-9` and
   `roll` is zero.
4. Car spacing is conserved: for every adjacent pair, `f_{i+1} = r_i − d · coupling_gap` to `1e-9`.
5. `direction = −1` mirrors the layout correctly: the consist extends in the increasing-station direction and
   each body's `forward` points toward decreasing station.
6. Clamping sets `clamped = True` and produces finite, non-NaN poses when the lead station is within one
   consist length of either alignment end.
7. The tram fixture poses correctly with a two-car tram consist and a 1000 mm base.
8. `pose_trainset_many` agrees with repeated `pose_trainset` calls to `1e-12`.
9. `shared/golden/trainset_chain.json` regenerates byte-identically on a second run.
10. `docs/data-contracts/trainset-chain.md` describes the algorithm in prose and formulae completely enough
    that T-123 can be implemented from it alone, without reading the Python.

## Out of scope

- Any client code.
- Suspension, bogie yaw relative to the car body beyond what the chord implies, hunting, or any dynamics.
- Coupler articulation for Jacobs bogies or shared-bogie units. If a catalogue entry needs that, note it and
  leave it for Phase 2.
- Exposing this over the protocol. T-114 ships `trainset.get` for the *consist specification*; the poses are
  computed client-side.

## Follow-up F10 — make the golden exercise cant roll

*Added 2026-09-18 after the T-112 review. Must land before T-123 implements the client chain against this
golden.*

`shared/golden/trainset_chain.json` is the only reference the Godot client will ever be measured against for
the trainset chain — T-123's implementation is pinned to it and nothing else. Every `roll` value in the
committed file is `0.0` or `-0.0`, because the Kralupy fixture's cant block is a documented zero placeholder.
Verified on review: the file contains exactly two distinct roll values, both zero.

That leaves a hole. A client implementation that averages the two pivots' rolls incorrectly, applies the
Gram-Schmidt correction in the wrong order, or ignores cant entirely would reproduce this golden perfectly
and still be wrong the moment it meets a canted curve. T-112 covered that behaviour on the Python side with
the synthetic tram fixture, which is the right call — but `tests/fixtures/synthetic/tram_loop.py` is a Python
module the Godot client cannot load.
